= Using the Guillotine API

Guillotine exposes content through a GraphQL schema generated from the content types and other schemas in your Enonic installation. Common fields such as `displayName` are available across content types; fields from your content model are exposed through generated types.

Use the <<playground#, Query Playground in Content Studio>> or a <<#third-party-clients, third-party GraphQL client>> to inspect the schema and try queries against a project and branch. The <<api#, API reference>> describes the built-in fields and types.

[#endpoint]
== Endpoint

For a deployment exposing XP's shared <<setup#api-base-url, API base URL>>, append `/com.enonic.app.guillotine:graphql` to that base to form the GraphQL endpoint.

With a local Enonic sandbox running on the default port `8080`, the API base URL is `http://localhost:8080/api`. With Guillotine installed, its endpoint is:

[source,text]
----
http://localhost:8080/api/com.enonic.app.guillotine:graphql
----

Production URLs depend on your deployment. See <<setup#endpoints, Setup>> for shared API bases, custom routes and site mounting.

[#content-context]
== Project and branch

At the Web endpoint, specify `project` and `branch` on the `guillotine` field, as shown in the query below. Use `master` for published content or `draft` for work in progress. Content permissions apply to the caller; querying `draft` normally requires authentication.

When Guillotine is mounted on a site, the endpoint supplies the project and branch, and query arguments cannot override them. See <<usage/site-context#, Site context>> for selecting a site within a project.

[#request-format]
== Request format

Send an HTTP POST request with `Content-Type: application/json` and a JSON body containing:

[%header,cols="1,1,4"]
|===
|Property |Type |Description
|query |String |The GraphQL query to execute.
|variables |Object |Optional. Values for variables declared by the query.
|===

The examples below use this local sandbox API base and retrieve up to ten root content items. For other environments, set the API base URL to the one exposed by your deployment. If Guillotine has an individual custom route, use that full endpoint URL. The queries use only built-in fields, so no custom content type is needed. Replace `myproject` with your project name. The project must contain published content readable by the caller to return a non-empty list.

[source,graphql]
----
query RootItems($project: String!, $branch: String!) {
  guillotine(project: $project, branch: $branch) {
    getChildren(key: "/", first: 10) {
      _id
      displayName
      type
    }
  }
}
----

[#third-party-clients]
== Third-party GraphQL clients

You can connect https://altairgraphql.dev/docs/[Altair] or another GraphQL client to Guillotine. Guillotine 9 serves the API without a query editor at its endpoint; the <<playground#, Query Playground>> is available in Content Studio.

To try the query above in Altair:

. Enter the full GraphQL endpoint URL: `<apiBaseUrl>/com.enonic.app.guillotine:graphql`. For a local sandbox running on port `8080` with Guillotine installed, use `http://localhost:8080/api/com.enonic.app.guillotine:graphql`.
. Use HTTP POST and `Content-Type: application/json`.
. Paste the `RootItems` query above into the query editor.
. Open the https://altairgraphql.dev/docs/features/variables[Variables] section and enter the JSON below, replacing `myproject` with your project name.
. Configure any authentication required by your deployment, then send the request.

[source,json]
----
{
  "project": "myproject",
  "branch": "master"
}
----

The client sends the query and variables together in the <<#request-format, request format>> described above. Use `draft` to query work in progress; content permissions apply, and draft access normally requires authentication. At a site-mounted endpoint, the endpoint determines project and branch.

Use Altair's https://altairgraphql.dev/docs/features/auth[authorization settings] or https://altairgraphql.dev/docs/features/headers[request headers] for the authentication mechanism supported by your deployment. A separate client needs its own authentication configuration to access protected content.

For a client running in a web page on another origin, configure <<configuration#config_file, CORS>> to allow that origin. If authentication uses cookies across origins, enable credentials in both the client and the CORS configuration.

[#curl]
== cURL

Save the query and variables as `request.json`:

[source,json]
----
{
  "query": "query RootItems($project: String!, $branch: String!) { guillotine(project: $project, branch: $branch) { getChildren(key: \"/\", first: 10) { _id displayName type } } }",
  "variables": {
    "project": "myproject",
    "branch": "master"
  }
}
----

Send the request:

[source,shell]
----
API_BASE_URL='http://localhost:8080/api'
curl "${API_BASE_URL}/com.enonic.app.guillotine:graphql" \
  -H 'Content-Type: application/json' \
  --data-binary @request.json
----

[#javascript]
== JavaScript

The same request can be sent with `fetch()`:

[source,javascript]
----
const apiBaseUrl = 'http://localhost:8080/api';

const query = `
  query RootItems($project: String!, $branch: String!) {
    guillotine(project: $project, branch: $branch) {
      getChildren(key: "/", first: 10) {
        _id
        displayName
        type
      }
    }
  }
`;

async function getRootItems() {
  const response = await fetch(
    `${apiBaseUrl}/com.enonic.app.guillotine:graphql`,
    {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        query,
        variables: { project: 'myproject', branch: 'master' }
      })
    }
  );

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }

  const result = await response.json();
  if (result.errors?.length) {
    throw new Error(result.errors.map(error => error.message).join('\n'));
  }

  return result.data.guillotine.getChildren;
}

getRootItems().then(console.log).catch(console.error);
----

For browser requests from another origin, configure <<configuration#config_file, CORS>> to allow the frontend origin. If your deployment uses cookie authentication across origins, the request also needs `credentials: 'include'` and the corresponding CORS credentials configuration.

[#response]
== Response

Both requests return the same JSON structure. The items depend on your project's content and permissions:

[source,json]
----
{
  "data": {
    "guillotine": {
      "getChildren": [
        {
          "_id": "531e40c9-6e5b-4259-b9e0-0d3144b2382a",
          "displayName": "My site",
          "type": "portal:site"
        }
      ]
    }
  }
}
----

GraphQL errors appear in an `errors` array and can accompany partial `data`, even when the HTTP status is successful. Check both the HTTP response and the GraphQL result. The JavaScript example treats any GraphQL error as a failed request; a client that supports partial results can handle the returned data separately.

[#troubleshooting]
== Troubleshooting

Check both the HTTP status and the response body. A successful HTTP status can still contain GraphQL `errors`; those errors identify fields or arguments that need attention.

=== Empty results or missing content

Confirm that `project` names the intended project and that `branch` is `master` or `draft`. Content must be published to appear in `master`. Also check the content path, query filters and the caller's read permissions. At a site-mounted endpoint, the request supplies project and branch even if the query specifies different values.

Query Playground uses your signed-in Content Studio user. A separate client may be anonymous or use another identity, so the same query can return different results. Compare requests using the same project, branch and caller.

=== Missing project or branch context

At the Web endpoint, explicitly pass both values, for example `guillotine(project: "myproject", branch: "master")`. An omitted value must come from the request context; when it is unavailable, context setup fails. See <<#content-context, Project and branch>>.

`siteKey` selects a site inside that project and does not replace project or branch selection. Supply it when using `getSite` or the `${site}` placeholder, and make sure the selected site exists in the requested branch.

=== Authentication or access failures

For `401` or `403` responses, confirm that the client sends the authentication expected by your deployment and that the caller can access the endpoint and content. Use the configured identity provider or gateway's authentication mechanism; installing Guillotine does not create a separate API credential.

A Content Studio login does not automatically authenticate another client. Configure its session or authorization headers separately. For cross-origin cookie sessions, use `credentials: 'include'` in browser requests and enable credentials for the frontend origin in the <<configuration#config_file, CORS configuration>>. Browser cookie restrictions still apply.

=== Browser CORS errors

If a request works in cURL or a desktop client but the browser reports a CORS error, inspect the `OPTIONS` preflight and the POST response in the browser's Network panel:

* `cors.origin` must allow the frontend's origin, including its scheme and port.
* The public route or proxy must pass `OPTIONS` requests through to Guillotine.
* Allowed methods must include `POST`, and allowed headers must cover those the client sends. Add `Authorization` if your authentication uses that header.
* For cookie credentials, use an explicit allowed origin and `cors.credentials=true`, together with `credentials: 'include'` in the client.

See <<configuration#config_file, Configuration>> for a complete example. CORS settings do not grant access to protected content.
